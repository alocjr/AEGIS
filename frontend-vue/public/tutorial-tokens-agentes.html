I · Ciclo ReAct — O que é

Pensa, age, observa — e repete

Um agente não responde de cara. A cada rodada ele faz três coisas: pensa (raciocina em texto o que fazer), age (chama uma ferramenta ou MCP) e observa (lê o resultado que voltou). Só então decide se responde ou se dá mais uma volta no ciclo.

Cada uma dessas três partes é gerada ou processada pelo modelo — e cada uma é tokens.

Um passo do ciclo ReAct
💭 Pensamento"Preciso da receita do 3T — vou consultar o ERP"
⚙️ Açãoconsultar_erp(periodo="3T")
👁 Observação{receita: 48200000, ...}
As três partes voltam para dentro do contexto — a próxima rodada começa lendo tudo isso de novo.
I · Ciclo ReAct — Memória do agente

O contexto é a única memória que o agente tem

O modelo não guarda nada entre uma chamada e outra — cada chamada é independente, como se fosse a primeira vez. Se uma informação não estiver dentro do contexto enviado agora, para o modelo ela simplesmente não existe.

É por isso que o histórico do ciclo ReAct precisa ser reenviado inteiro a cada passo: não é redundância, é a única forma do agente "lembrar" do que pensou, fez e observou até ali.

Memória = o que está no contexto agora
🧠 Dentro do contexto

System prompt, ferramentas, pergunta, histórico do ciclo, arquivos anexados — tudo isso é a memória do agente nesta chamada.

🚫 Fora do contexto

Qualquer coisa que não caiba ou não seja reenviada — deixa de existir para a próxima chamada. O agente "esquece".

Todo o resto deste tutorial é, na prática, sobre o preço de manter essa memória viva a cada passo.
I · Ciclo ReAct — Arquivo no contexto

Anexe um arquivo à memória do agente

Um relatório, uma planilha, uma base de conhecimento — quando um arquivo entra no contexto, ele também vira memória. E, como toda memória do agente, ele precisa ser reenviado a cada passo do ciclo, não só uma vez.

I · Ciclo ReAct — Por que cresce

O contexto nunca reseta

Não existe "chamada leve" no meio do ciclo. Toda vez que o agente pensa de novo, o modelo recebe: o system prompt, a definição das ferramentas, a pergunta original — e o histórico acumulado de tudo que já foi pensado, feito e observado até aquele ponto.

É por isso que o último passo de um ciclo longo custa muito mais que o primeiro, mesmo sendo, na prática, "só mais uma pergunta ao modelo".

III · Sistemas multiagentes — O que muda

Um orquestrador, vários agentes

Em vez de um agente fazendo tudo, um orquestrador recebe a tarefa e a divide entre subagentes especializados — cada um com seu próprio system prompt, suas próprias ferramentas e seu próprio ciclo ReAct interno.

O orquestrador não vê o raciocínio interno de cada subagente — só recebe o resumo do resultado. Mas para cada subagente, aquele ciclo interno inteiro aconteceu, e foi pago.

III · Sistemas multiagentes — Quantos subagentes

Escolha quantos subagentes entram

Cada subagente que você adiciona soma seu próprio ciclo completo — não é uma fração do custo do agente único, é um agente inteiro a mais. O cálculo aqui assume delegação sequencial (o orquestrador aciona um subagente, recebe a resposta, aciona o próximo): é o padrão mais comum quando uma tarefa depende do resultado da anterior — e também o mais caro, porque o orquestrador reprocessa seu próprio histórico de delegações a cada acionamento.

III · Sistemas multiagentes — De onde vem o custo

Orquestrador vs. subagentes

O orquestrador sozinho já cresce como um agente único — ele reprocessa seu próprio histórico de delegações a cada chamada. Mas a maior fatia do custo, normalmente, está no trabalho interno de cada subagente.

Se a delegação fosse paralela — 1 chamada despachando todos os subagentes, 1 chamada recebendo todos os retornos — o overhead do orquestrador cairia bastante. O custo de cada subagente, porém, não muda: o ciclo interno de cada um é pago do mesmo jeito.
